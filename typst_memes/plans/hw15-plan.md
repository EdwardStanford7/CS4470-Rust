# hw15 port plan

## What hw15 actually exercises
Confirmed via `grader/grader.py` lines ~502-507 and reading test samples:

- Part 1 (`ok1/`, DiffSpec, `-s`): struct/bool-expr heavy small programs (e.g. `show true && false`).
- Part 2 (`ok2/`, DiffSpec, `-s`): larger named programs (badge, blu, ...) — full-language exercise, images/structs/commands together.
- Part 3 (`ok3/`, **OptSpec**, `-s` vs `-s -O3`): requires an actual optimization pass — `.expected` (no opt) AND `.expected.opt` (optimized) must both match. This is new work beyond plain codegen: constant folding / dead code / register-reuse or whatever the reference does under `-O3`.
- Part 4 (`fail-fuzzer1/`, InvalidSpec, **`-t`**): typecheck-only rejection of fuzzed programs. This is **front-end**, not codegen — orthogonal to the assembly port. No `.expected` files exist for these (just must fail).
- Part 5/6 (`ok-fuzzer1/`, `ok-fuzzer2/`, DiffSpec, `-s`): fuzzed full-language programs exercising structs, arrays, nested indexing, `sum`, `array`, all commands.

hw15 is the "everything" assignment: structs (literals + field access `.field`), and the command forms `show`, `read image`, `write image`, `print`, `time`, `assert` as top-level commands (as opposed to hw-earlier's statement-level `assert`/`let`/`return` inside functions). **The front-end (parser + typechecker) already fully supports all of this** — see compiler.typ lines 5-7 (keywords), 90/97-106 (formatting `struct-lit`, `AssertStmt`, `ReadCmd`/`WriteCmd`/`PrintCmd`/`AssertCmd`/`ShowCmd`/`TimeCmd`/`StructCmd`), 145 (struct-lit parsing), 155-165 (statement/command parsing incl. `read image`/`write image`/`time`/`struct` decl), 184-219 (struct registration, duplicate/recursive-struct checks, dot-field typecheck, command typecheck). So **hw15's incremental work is almost entirely in the assembly/codegen layer**, plus the `-O3` optimizer for part 3, plus verifying fail-fuzzer1 typecheck rejections already work (likely already covered by earlier hw's typechecker — just needs a grader run, no new code expected).

## Reference algorithm (origin/main:src/assembly.rs) to port

Structs have **no padding** — flat concatenation of field sizes (ast.rs `Type::Struct::isize()/usize()`: `size = sum of each field's isize()/usize()`; every scalar field is 8 bytes, so a struct is just `8 * total_scalar_field_count` bytes, stored on the shadow-stack as a contiguous run of 8-byte slots, fields in declaration order).

Key functions/logic (line numbers in the ported blob, i.e. `git show origin/main:src/assembly.rs`):

- **`ExpressionType::StructLiteral`** (~1283-1298): push assert-guard, generate each field expression **in reverse order** (`fields.iter().rev()`) so on the stack fields end up in forward declaration order, `remove_shadow()` for each field's shadow entry, then `add_shadow_type(&expression.resolved_type)` (one combined struct shadow entry). No actual move/copy instructions needed — the fields are already contiguous on the stack from evaluating them back-to-front; the struct literal is a shadow-stack bookkeeping op only.
- **`ExpressionType::Dot`** (~1299-1339): generate the struct-variable expression (pushes the whole struct on stack). Compute `offset_into_struct` = sum of `usize()` of fields before the target field (in declaration order), and `field_type`. Then copy the field's bytes to the top of stack via a reversed byte-copy loop: for `i in (0..field_type.usize()).step_by(8).rev()`, `mov r10, [rsp + offset_into_struct + i]` then `mov [rsp + struct_size - field_size + i], r10`; then `add rsp, struct_size - field_size` to pop the rest of the struct, leaving just the field. Update shadow stack: remove struct type, add field type.
- **Struct as function parameter** (~451-456): like arrays, computed via a `data_pointer` offset (`-arr_param_size - 16`) into caller's pushed-by-reference struct data — struct args are passed **by shadow-stack convention identical to arrays** (i.e., the struct's data lives in caller-allocated stack space referenced by a fixed offset), not by individual register-per-field. Mirror exactly what's done for `Type::Array` param handling just above it (lines ~439-450) since it's the same offset scheme, `arr_param_size += param.1.isize()`.
- **Struct as return type** (~334-341): `mov rax, [rbp - 8]` (the caller-supplied out-pointer, same slot used for array returns), then loop `for i in (0..return_type.isize()/8).rev()`, `mov r10, [rsp + i*8]` / `mov [rax + i*8], r10` — byte-for-byte identical to the `Array` return case just above it. Struct and Array returns are handled identically (both are "returned via out-pointer written by caller in `[rbp-8]`").
- **`CommandType::Struct`** (~596-599): **no-op** at codegen time — struct *declarations* generate nothing (they're purely a typechecking-time construct; codegen only cares about `Type::Struct` values flowing through expressions).
- **`CommandType::Show`** (~368-389): push assert-guard; `print_shadow_stack()` (debug-only — likely a no-op / cfg'd out in release, check if it emits real instructions or is a debug print — if it's just internal Rust-side debug logging, skip porting it); `pad_shadow_with(expression)` (align/pad shadow stack to some alignment before evaluating, mirrors `pad_shadow()` used elsewhere before calls); generate the expression; insert the show-format string constant via `get_show_format_string(type)` (recursive: struct → `"(TupleType t1 t2 ...)"`, array → `"(ArrayType elt rank)"`, scalar → type's Display, e.g. `"(IntType)"`/`"(FloatType)"`/`"(BoolType)"` as seen literally in `grader/hw10/ok-fuzzer2/007.jpl.expected` constants); `add_shadow_type(&Type::Int)` (the format-string pointer itself is pushed as a shadow int); `lea rsi, [rsp]` / `call _show`; unwind: `add rsp, expression.resolved_type.usize()`, `unpad_shadow()`, `remove_shadow()`.
- **`CommandType::Print`** (~552-560): insert string constant for the literal message, `pad_shadow()`, `call _print`, `unpad_shadow()`.
- **`CommandType::Read`** (~480-534): `sub rsp, 24` (reserve 3 shadow slots: data ptr + 2 dims for a rank-2 array), shadow-type = `Array{element: rgba struct, rank: 2}`, `lea rdi, [rsp]` (out-pointer for the runtime to fill), `pad_shadow()`, load filename string constant into `rsi` (via `lea rsi, [rel constN]`), `call _read_image`, `unpad_shadow()`. Then record `destination`'s (and, if array-lvalue destructuring, each dimension binding's) stack offset in the offset table exactly like a `let`.
- **`CommandType::Write`** (~536-550): `pad_shadow_with(source)`, generate `source` expression (the rgba[,] array), insert destination filename string constant, `call _write_image`, unwind (`add rsp, source.resolved_type.usize()`), `unpad_shadow()`.
- **`CommandType::Time`** (~561-594): call `_get_time` before and after generating the *inner command* (`time` wraps another command — `time print ...`, `time assert ...`, etc.), push/store both timestamps as floats on the shadow stack, `subsd` to get elapsed, then `call _print_time` with the elapsed float. Note the inner command is generated recursively via `self.generate_command(asm_function, command)` — so `time` must dispatch back into the same command-codegen switch, meaning Typst's command-codegen function needs to be written to allow this recursive call (structure it as one function handling all `CommandType`s, called both top-level and from the `Time` case).
- **`StatementType::Assert`** vs **`CommandType::Assert`** (~354-362 / ~600-608): identical logic (condition→cmp→jne→fail), just top-level vs inside-function variants — the only difference is `in_statement` bool passed to `generate_expression`. Port as one shared helper parameterized by that flag.
- **`assert()` helper** (~2060-2069): shared by all assert-like failure paths — allocate a fresh `.jumpN` label, emit the comparison jump `{cmp_mode} {label}`, `pad_shadow()`, insert the message string constant, `call _fail_assertion`, `unpad_shadow()`, then the jump-target label. Port as a single function used by both `assert` statement/command AND any implicit bounds/index assertions from earlier assignments (hw11-13) — reuse, don't duplicate.
- **`get_show_format_string`** (~2075-2095): pure recursive string builder over `Type` — trivial to port, needed for `show`.

## Proposed Typst implementation
Extend whatever `asm.typ` module the hw10-14 port produces (same `AsmFunction`-equivalent struct: body string, stack_size counter, shadow_stack list, assert_stack list) rather than a separate file — struct/command codegen slots into the existing `generate-expression` / `generate-statement` / `generate-command` dispatch functions as new match arms. Concretely:

1. Add `struct-lit` and `dot` arms to `generate-expression`, following the exact instruction sequences above.
2. Add a `generate-command` function (if not already present from earlier hw's `let`/`fn` commands) with arms for `show`, `read`, `write`, `print`, `time`, `assert`, `struct` (no-op), `fn`, `let` — `time` recurses into this same function.
3. Extend the function-parameter and function-return codegen (already exists for scalars/arrays from hw11-13) with a `Type::Struct` branch that is **byte-identical** to the `Type::Array` branch (same offset math, same out-pointer convention) — do not special-case struct layout beyond size.
4. Add `get-show-format-string(type)` recursive helper.
5. Reuse the existing `assert`-with-jump-label helper (must already exist for earlier hw's runtime bounds checks — hw11/12 array indexing needs this) for both statement- and command-level `assert`.
6. `-O3` optimizer (part 3 only): **treat as a separate, later step** — get ok1/ok2/fail-fuzzer1/ok-fuzzer1/ok-fuzzer2 (parts 1,2,4,5,6) to 100% first using unoptimized codegen for both `-s` and `-s -O3` (i.e., initially make `-O3` a no-op flag, which will pass every part except ok3's second diff against `.expected.opt`). Only then reverse-engineer the optimization from diffing `.expected` vs `.expected.opt` on the ok3 samples (col/dns/matmul/pixel-sort/sft/upscaler) to find what transform(s) are needed — likely dead local elimination, constant folding, or peephole reg reuse; inspect the diffs directly rather than re-deriving from assembly.rs (grep assembly.rs / main.rs for `O3`/`optimiz` flags to see if the same binary implements it, or if it's a separate pass file not yet located).

## Gotchas
- Struct fields are **all 8 bytes** in this language (int/float/bool/void), so "layout" is trivial — no alignment/padding logic needed, unlike a real C struct.
- Struct literal field evaluation order is **reversed** relative to declaration order (stack grows down, so evaluate last-declared field first) — get this backwards and every multi-field struct test fails.
- Struct param/return sharing the exact array convention means: if the hw11-13 array parameter/return code isn't already factored into a reusable helper, structs risk copy-pasted logic drifting out of sync — factor `Type::Array | Type::Struct` into one shared branch (mirrors the Rust `matches!(return_type, Type::Array{..} | Type::Struct{..})` pattern used throughout assembly.rs).
- `print_shadow_stack()` calls scattered through `Show` codegen are almost certainly a debug/assert-only instrumentation hook in the Rust source (verify: check its definition — if it only runs under `debug_assertions` or is a no-op in the compiled binary's normal path, it must NOT emit real instructions in the Typst port, or diffs will fail immediately).
- `fail-fuzzer1` needs zero codegen work — confirm via a grader run only; if any of those 60 cases unexpectedly pass typecheck, that's a **front-end** bug to report back, not something for the assembly port to fix.
- Don't forget: struct declarations (`CommandType::Struct`) must still be **parsed/typechecked but must emit nothing** in codegen — a no-op arm, not a missing/panicking one.

## Ordered checklist
1. Confirm fail-fuzzer1 (part 4) already passes via typecheck alone (no codegen change needed) — quick grader sanity check.
2. Port `get-show-format-string`.
3. Port struct-literal + dot-access expression codegen.
4. Extend param-passing and return-value codegen to treat `Struct` identically to `Array`.
5. Implement `generate-command` arms: `struct` (no-op), `print`, `read`, `write`, `time` (recursive), `show`, `assert` — reusing the shared assert/jump-label helper.
6. Run parts 1, 2, 5, 6 (`ok1`, `ok2`, `ok-fuzzer1`, `ok-fuzzer2`) to 100% with `-O3` as a no-op flag; run part 4 to confirm already-green.
7. Only then tackle part 3 (`ok3` OptSpec): diff `.expected` vs `.expected.opt` on the 6 sample programs to reverse-engineer the required optimization, implement it behind `-O3`, verify both the unoptimized and optimized diffs pass for all 6.
