# hw13 port plan: `-O1` peephole/local optimizations

## 1. What's new in hw13

hw13 introduces **no new language features**. All 5 parts (`ok1`..`ok5`) are
`OptSpec` tests (see `grader/grader.py:491-496`): each `.jpl` is compiled
twice, once plain (`-s`, must match `NNN.jpl.expected`) and once with
`-O1` (`-s -O1`, must match `NNN.jpl.expected.opt`). So the *unoptimized*
codegen must already be complete/correct (carried over from hw10-12); hw13
only adds an alternate, optimized code path selected by an `-O1` flag.

Diffing `.expected` vs `.expected.opt` per part shows exactly 3 independent
peephole optimizations:

- **ok1** (`show 12`): small integer literals become x86 immediates
  (`push qword 12`) instead of a `.data` `dq` constant + `mov rax,[rel ...]`.
  The `dq` constant for that value is dropped entirely from `.data`.
- **ok2** (`show if true then 1 else 0`): a compile-time-constant `if`
  condition (literal `true`/`false`) is folded away — only the taken
  branch's code is emitted, no `cmp`/`je`/jump-labels at all, and the dead
  branch's constants also vanish from `.data`.
- **ok3** (`show array[i : argnum] [i,i,i]`) and **ok4**
  (`show argnum * 256`): multiplication where one operand is a
  power-of-two integer literal becomes a `shl`. ok4 diff:
  `pop r10; imul rax, r10` → `shl rax, 8` (256 = 2^8); the `256` `dq`
  constant is also dropped since it's folded into the shift amount.
  ok3's diff (`mov rax,0; imul rax,[rsp+24]; add rax,[rsp+16]; imul rax,16`
  → `mov rax,[rsp+16]; shl rax,4`) is the *same* rule applied inside linear
  index calculation for an array literal comprehension of rank... (see
  gotcha below — this is generated by whatever computes the flattened
  offset for the comprehension body, using element_size=16 there; treat it
  as "any `imul reg, <power-of-two>` in codegen becomes `shl reg, log2(n)`
  when optimizing", not a special case).
- **ok5** (`let a = [1,2,3]; show a[1]`): combination of ok1's immediate
  folding (array literal elements `1,2,3` become `push qword N` instead of
  loading `dq` consts) — the array-index-bounds-check machinery itself is
  otherwise unchanged in this example (still emits the negative/too-large
  checks) — only the literal-push optimization applies here, not a bounds
  check elimination as I initially guessed. Confirm with the full diff
  before assuming otherwise.

## 2. Relevant assembly.rs logic

Reference file: `origin/main:src/assembly.rs` (read via
`git show origin/main:src/assembly.rs` from CS4470-Rust root — do not
checkout). Grep for `optimization_level` (7 call sites):

- `insert_int_constant` (~line 2037): if `optimization_level > 0 &&
  is_32_bit(number)`, emit `push qword {number}` instead of allocating a
  `.data` constant. **This is ok1/ok5.**
- The `*` binary-op arm in `generate_expression` (~lines 754-816):
  if `optimization_level > 0` and either operand is a literal int that is
  32-bit-or-power-of-two, special-cases:
  - both operands literal power-of-two-ish → still generic `imul` on two
    immediates pushed (not exactly a shift — check this arm's exact output
    doesn't apply to ok4's single-immediate case).
  - one operand literal and `value != 1`: emits `imul rax, {value}`
    (immediate multiply), **not `shl`**.
- `calculate_linear_index` (~line 1920): when optimizing, folds a known
  power-of-two/32-bit bound directly into `imul rax, {value}` instead of
  loading it from the stack — also uses `imul`, not `shl`.
- `optimized_array_index` (~line 1044, from commit `99997c4`, "index
  expression optimization"): rewrites `a[i,j,...]` on a plain variable
  array (not `from_main` main-body case) to compute all index/bounds
  checks up front and copy element data directly, avoiding recomputation.
  This is a structural rewrite, not a peephole — **not exercised by
  hw13's 5 sample tests directly** but likely relevant to the larger
  fuzzer-based grading set if any exists beyond `ok1..ok5`.
- if-branch handling has a general "both branches identical" collapse
  elsewhere in the file (search `jump_label` / the block right before line
  ~740) — inspect that for how constant-condition folding could piggyback
  on it, or whether constant-condition folding needs to be added as a new
  check ahead of normal `if` codegen.
- `insert_float_constant`: **no optimization branch at all** — floats
  always go through `.data`. Don't try to optimize floats.

### CORRECTED 2026-09-05: no imul/shl mismatch — it's a final regex post-pass

**The claim below (originally in this section) that origin/main emits raw
`imul` and would fail the `.expected.opt` diff is WRONG — verified against
the actual reference source.** `origin/main:src/assembly.rs` has a
`string_replacement_optimization` function (~line 2103-2137) that runs as a
**whole-text regex post-pass** over the *entire* generated assembly string,
only when `optimization_level > 0` (called from `generate_assembly` at
~line 2142-2147, right before returning):
1. `\bimul rax, (\d+)\b` → if the captured number is a power of two,
   replace with `shl rax, {trailing_zeros}`; otherwise leave unchanged.
2. `\bimul rax, 1\b` → deleted entirely (empty string).

So origin/main's codegen proper emits `imul rax, {value}` uniformly at
*every* site (the `*` binop arm, `calculate_linear_index`, array bounds/
offset math — all of them, no special-casing per call site), and this
single textual regex pass at the very end converts the power-of-two ones to
`shl` and drops the identity ones. That's exactly why the same rule shows
up consistently across ok3's linear-index computation, ok4's binop, and any
other `imul rax, N` site — it's one mechanism, not independently-implemented
per-site logic.

**Verified against real fixtures** (`grader/hw13/ok3/003.jpl.expected` vs
`.expected.opt`): confirms `imul rax, 16` → `shl rax, 4` inside the
comprehension's linear-index calc, matching this post-pass exactly (16 is
`element_size`, a compile-time constant, run through the *same* regex as
the binop case — not a separate "linear index knows about shl" code path).

**Implementation guidance (revised):** do NOT hand-roll a "is this operand a
literal power-of-two, if so emit shl" branch at every multiply site (per
the original point 3/5 below) — instead, emit `imul rax, {value}`
unconditionally at every "multiply the top-of-stack-or-computed value by a
known-at-codegen-time integer constant" site (same as `-O0`), and add ONE
post-processing pass over the final assembly string (Typst: a couple of
`.replace()`/regex-equivalent calls, or manual line-scan since Typst's
regex support may be limited — check) applying the same two rules, gated on
`opt-level > 0`. This is simpler, structurally matches the reference
exactly, and automatically covers every current and future `imul rax, N`
site without per-site duplication. ok4's non-power-of-two 32-bit literal
case (if any exist in that directory) is then trivially correct too, since
the post-pass leaves non-power-of-two `imul` untouched. This does NOT
change point 1/2's `insert_int_constant` optimization (immediate literal
push, unrelated to this regex pass) — those stay as originally described.

## 3. Proposed Typst implementation approach

Build on whatever `asm.typ` module the hw10-12 port produces (function
that emits per-statement/expression instruction lists from the typed
AST). Add:

1. A `opt-level` parameter threaded through the codegen entry point (0 or
   1), coming from the `-O1` CLI flag in `jplc`/`cli-query.typ` (check how
   `-O*` is currently parsed — `jplc` already has a catch-all `-O*) ;;`
   no-op case; it needs to actually set a mode/level and pass it through
   `compile(...)`).
2. `insert-int-constant(n, opt-level)`: if `opt-level > 0` and `n` fits
   32-bit signed range, return an instruction `push qword {n}` directly
   (no dedup/const-table entry). Else fall back to existing
   const-table + `mov`/`push` path. **Must not register the constant in
   the dedup table when short-circuited**, else you'll emit unused `dq`
   entries and fail the "constant dropped from `.data`" part of the diff.
3. Multiply codegen: when either literal operand (checked structurally,
   not just resolved-integer-with-unknown-value) is a compile-time integer
   literal:
   - if `opt-level > 0` and the literal is a power of two and != 0:
     generate the non-literal operand, then `shl <dest>, {log2(n)}`
     (skip generating the literal operand's code/const at all).
   - elif `opt-level > 0` and literal is 32-bit-representable and != 0:
     generate non-literal operand, `imul <dest>, {n}`.
   - else fall through to generic push-both/`imul`/`pop` path.
   Must handle literal-on-either-side (left or right operand).
4. Constant-`if` folding: before emitting the general if/else
   compare-and-jump sequence, check if the condition expression is
   structurally a boolean literal; if so, only recurse into the taken
   branch's statement/expression codegen (drop the other branch's
   constants and all label/jump instructions).
5. `calculate_linear_index`-equivalent (wherever the port implements
   array-literal/comprehension flattened offset computation): apply the
   same literal-bound → `shl`/`imul` rule as point 3 when a bound is a
   compile-time literal.
6. Wire `opt-level` into every codegen entry recursively (it's a `where`
   condition thread throughout AsmFunction generation in Rust — the Typst
   port should thread it as a plain function argument or a state
   dictionary field, whichever style the rest of the port already uses).
